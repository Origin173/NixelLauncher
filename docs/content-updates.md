# 普通内容更新的依赖规划

实例内容页的单项和批量更新统一走 `content.update {instanceId, updates}`，每个目标保留来源、项目 ID 和准确版本 ID。

任务首先重新扫描实例，按来源把所有所选目标交给同一次 `ResourceProvider.planInstall`。Modrinth 与 CurseForge 都使用现有多根依赖解析器，先固定所选版本，再递归解析必需依赖、检查版本冲突、禁用依赖和互斥内容。全部来源的计划和目标文件冲突检查通过后，才按返回的固定下载列表调用共享文件安装器，不再逐根重新解析安装。

例如 A2 固定依赖 B1，而用户同时选择 A2 和 B2，无论点击顺序如何都会在任何内容文件写入前失败；不会先写入 A2/B1 再用 B2 覆盖依赖。

## 提供者契约

```ts
planInstall?(
  roots: VersionContentRoot[],
  instance: Instance,
  retained: InstalledContent[],
  signal?: AbortSignal,
  options?: { pinRetained?: boolean },
): Promise<ContentDownload[]>
```

`pinRetained` 缺省为 `true`：已保留的项目版本固定，版本与内容联动流程保持原语义。普通内容更新传 `false`，允许必需依赖升级未选项目，保留原先单项更新的行为；明确选择的根版本仍始终固定。`retained` 包含同一来源的非根已安装记录，仍用于启用状态和互斥检查。

两个内置来源直接将该选项交给现有 `resolveContentPlan` 的 `pinInstalled` 参数。第三方提供者可以继续只支持更保守的规划并明确报告冲突；未实现 `planInstall` 的提供者无法执行 `content.update`，命令会在写盘前明确报错，资源浏览和已有的单次 `install` 契约保持不变。管理插件不会回退到存在顺序依赖的逐根安装。

管理插件还检查计划包含每个准确根版本、返回文件来源一致、同一项目没有不同版本，以及跨来源文件名没有冲突。启用与禁用状态沿用已有文件安装器。

## 取消与重试

保留当前部分完成语义：取消或下载失败后已经提交的内容保留，尚未提交的文件由下载器处理。重试始终保留原始全部根目标，先重新解析和验证完整依赖图，包括已经更新到目标版本的根；只有完整计划通过后，才跳过已完成的文件。这使后续失败再重试时仍会发现已完成根与其余目标的依赖冲突。

隔离验证使用真实 Modrinth / CurseForge 提供者、Host 任务与下载插件，以及可控 API/下载响应；不需要在线凭据。验证覆盖双顺序固定依赖冲突、跨来源互斥冲突前零内容文件写入、部分完成后重试重新验证完整图、依赖升级、禁用状态保留与取消重试。
